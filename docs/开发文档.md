## 1. 项目背景

在数据库开发、测试、演示场景中，常常需要大量"看起来真实、且各表之间能正确关联"的测试数据。手工造数或简单的随机造数存在两个核心痛点：

- **数据无语义**：字段被填充为无意义的随机字符串（如 `aXf83Kd...`），无法用于演示、培训或贴近真实业务的测试。
- **多表关联断裂**：随机生成的外键值在主表中不存在，导致 `JOIN` 查不到数据，无法验证关联逻辑。

尤其在金融、银行等领域，数据库通常采用 **Apache Doris / StarRocks** 等 OLAP 引擎，其建表语句**没有显式 `FOREIGN KEY`**（关系靠共享字段语义隐式表达），且字段普遍带有中文 `COMMENT`。这给"既要语义真实、又要关联一致"的造数提出了更高要求。

DataForge 即为解决这些问题而设计，目标是：

1. **语义化生成**：结合字段名、中文注释、数据类型，生成贴近业务的真实数据（中文姓名、身份证号、银行卡号、合理金额、YYYYMMDD 日期等）。
2. **多表逻辑闭环**：保证任意路径的关联查询都能命中，即使通过不同字段名（如 `cust_no` 与 `party_id`）、不同中间表关联到同一语义实体，结果也一致。
3. **可视化交互 + 内嵌数据库**：无需额外部署数据库即可解析 Schema、生成数据、即时用 SQL/Cypher 查询验证。
4. **AI 增强（可选）**：用大模型识别业务域、推断字段规则、识别表间关系、把自然语言转成生成规则。

## 2. 功能特性

| 模块 | 能力 |
|------|------|
| **Schema 解析** | 解析 SQL DDL（MySQL / PostgreSQL / SQLite / Doris 等）、Cypher 图 Schema；支持多文件合并 |
| **语义化数据生成** | 基于中文注释 + 字段名 + 类型的银行域规则；Faker `zh_CN` 本地化 |
| **多表关系闭环** | 共享键池 + 传递性根解析，保证跨表、跨字段名、跨路径的 JOIN 一致 |
| **表关系图谱** | AI / 启发式识别表关系；导入 / 导出 Cypher；图可视化 + 表格编辑 |
| **自定义规则** | ① 自然语言描述（AI 翻译）② 样例数据（INSERT/CSV）统计识别 ③ 手动编辑 |
| **内嵌关系库** | DuckDB 存储生成结果，提供 SQL Explorer |
| **内嵌图库** | Kuzu 存储图数据，提供 Cypher Explorer（可选） |
| **多格式导出** | CSV / JSON / SQL / Excel(xlsx) / Cypher |
| **MySQL 写入** | 将生成的数据直接写入外部 MySQL |
| **流式生成** | WebSocket 实时进度推送，适合大批量生成 |

### 4.2 内部 Schema 模型（统一中间表示）

所有解析器（DDL / Cypher）都输出统一的 `RelationalSchemaModel`，作为整个系统的"单一事实来源"：

```
RelationalSchemaModel
├── id: str                       # schema 唯一标识
├── dialect: str
├── schema_type: "relational" | "graph"
├── tables: [TableDef]
│   ├── name, primary_key, foreign_keys, unique_constraints
│   └── columns: [ColumnDef]
│       └── name, type_category, nullable, primary_key,
│           length, precision, scale, enum_values, comment  ← 注释是语义关键
├── generation_order: [GenerationStep]   # FK 安全的拓扑生成顺序
├── field_specs: {"table.col": spec}     # 持久化的自定义规则
└── nodes / relationships                # 图 Schema 专用
```

Schema 实例由 `SchemaRegistry`（进程内内存注册表）按 `id` 管理，后续生成、导出、关系编辑都通过 `schema_id` 引用同一实例。

## 6. 核心实现思路

### 6.1 DDL 解析（含 Doris/OLAP 适配）

`app/core/ddl_parser.py`：

- 基于 **sqlglot** 多方言解析 `CREATE TABLE`，提取列、类型、约束。
- **Doris/StarRocks 预处理** `_preprocess_doris()`：通过括号深度跟踪定位列定义块的闭合括号，剥离 sqlglot 无法解析的 `DUPLICATE/UNIQUE/AGGREGATE KEY(...)`、`PARTITION BY`、`DISTRIBUTED BY`、`PROPERTIES(...)` 等尾部子句。
- **主键回退**：Doris 表无标准 PK，剥离前先提取 `DUPLICATE KEY(...)` 列作为表的 `primary_key`（仅用于展示/元数据，不强制单列唯一，避免误把分区列如 `etl_dt` 强制唯一）。
- **注释提取**：捕获 `CommentColumnConstraint`（如 `COMMENT "信用卡卡号"`）写入 `ColumnDef.comment` —— 这是语义化生成的核心线索。
- 类型映射为统一的 `type_category`（integer/float/decimal/string/text/boolean/date/datetime/json/enum）。

### 6.2 多文件合并与关系注入

`app/core/schema_merge.py`：

- `merge_ddl_schemas()`：把多个 DDL 文件解析并合并为单一 Schema（表名为键，去重）。
- `inject_relations()`：把"表间关系"作为 `ForeignKeyDef` 注入对应表，仅当两端表和列都存在时生效。
- `recompute_generation_order()`：基于 FK 用 **Kahn 拓扑排序**重算生成顺序；遇到环时按入度最小的节点强制破环（容错不报错）。

### 6.3 表间关系：解析、推断与序列化

- **Cypher 关系图解析** `relation_parser.parse_schema_graph()`：解析"schema graph"格式（`MATCH (a:Table {fqn}) MATCH (b:Table {fqn}) MERGE (a)-[r]->(b) SET r.via='child_col → parent_col'`），约定 MERGE 箭头为 `子表 → 父表`，`via` 左侧为子列、右侧为父列。处理箭头（→/->/↔）、斜杠（或）、括号注释等多种写法。
- **关系序列化** `relations_to_cypher()`：把关系导出为可被上面解析器反向读取的 Cypher（可往返）。
- **AI / 启发式关系推断** `app/ai/relation_infer.py`：
  - LLM 模式：将"表名 + 关键列 + 中文注释"的精简签名发给大模型，可识别**跨字段名**的同义关系（如 `cust_no ↔ party_id`）。
  - 启发式回退（无 LLM）：连接多表共享的同名关键列，并过滤出现在过半表中的"泛在维度列"（如机构号）以降噪。

### 6.4 约束求解与逻辑闭环（核心）

`app/generator/constraint.py` 的 `ConstraintSolver`：

- **共享键池**：按 `(表, 列)` 维度维护值池。父（权威）列生成后 `register_values`，子列从中 `sample_values`，保证子列值必然存在于父列 → JOIN 必然命中。
- **传递性根解析** `_resolve_root`：把外键目标沿链路解析到**根权威列**。例如 `A.cust_no → B.cust_no → … → C_PT_INDV_CUST_BASIC.party_id`，所有客户引用最终都从同一个根池采样。
- **效果**：所有"语义相同但字段名各异"的列（`cust_no`/`ecf_party_id`/`party_id`/`userid` 等）共用同一取值空间。**实测 82 表 / 103 个外键列 100% 闭环、0 孤儿**；不同路径关联到同一实体时，因根列唯一，结果完全一致。

### 6.5 语义化数据生成

- `app/generator/semantic_zh.py`：中文注释 → 银行域规则。关键约定：
  - `日期` + 数值类型 → **YYYYMMDD 整数**（银行常见存储约定）；`日期` + DATE 类型 → 真实日期。
  - `金额/余额/额度` → 合理金额；`时点值`（数值）≠ 时间戳；`卡号` → 银行卡号；`证件号` → 18 位身份证；`状态/标签` → 代码；`机构名称` → 机构名等。
- `app/generator/rules.py`：Faker 引擎默认 `zh_CN`，新增 `cn_*` 系列标签（cn_name / cn_id_card / cn_bankcard / cn_money / cn_date_int 等）；`Rule` 支持 `value_pool`、`pattern`、范围、日期区间等。
- `app/generator/strategies/rule_based.py` 的 **四层优先级**（高→低）：
  1. **关系 FK 采样**（从父池采样，保证闭环）
  2. **自定义/ AI 规则**（`field_specs`）
  3. **中文注释语义**（`semantic_zh`）
  4. **英文字段名 / 类型回退**（原 Faker 规则）
- **类型兼容守卫** `_enforce_type`：数值列必给数值、日期列必给时序值，防止类型不兼容导致写库失败。

### 6.6 自定义规则（两种来源 + 手动）

字段规则统一为 `field_specs`（`"表.列" → spec`），持久化到 Schema，生成时优先级最高。支持的 spec 类型：`enum` / `pool` / `pattern` / `int_range` / `decimal_range` / `date_range` / `faker`。

- **自然语言** `app/ai/custom_rule.py`：把中文描述（如"年龄18到60之间；手机号138开头；状态只能是正常/冻结/销户"）经 LLM 翻译为结构化 spec，带列上下文校验。
- **样例数据识别** `app/generator/sample_infer.py`（**纯统计，无需 LLM**）：解析 INSERT SQL（sqlglot）或 CSV，对每列取值统计推断：
  - 整数低基数(≤6) → `enum`；定长 ≥11 位 → `pattern`；否则 → `int_range`
  - 小数 → `decimal_range`（含小数位）；日期 → `date_range`
  - 文本低基数 → `enum`；中基数(≤50) → `pool`

### 6.7 高性能批量写入

`app/db/duckdb_client.py`：DuckDB 的逐行 `executemany` 极慢（1 万行约 290s）。改为**写临时 CSV → `read_csv_auto` 向量化批量加载**，1 万行降至约 0.14s（约 2000× 提速）。同时对大整数浮点、含换行的字符串做清洗，避免科学计数法/多行错位导致的写入错误。

### 6.8 AI 流水线（LangGraph，可选）

`app/ai/`：`seed.py`（按表推断字段生成规范）、`nodes.py` / `pipeline.py`（LangGraph 节点：SchemaContext → RuleInference → BatchGen → Validation）、`llm_config.py`（构建任意 OpenAI 兼容 LLM）。AI 不可用时自动降级到规则生成。

## 7. 对外接口

基础路径前缀 `/api`（WebSocket 除外）。所有请求/响应均为 JSON（导出与关系导出除外）。

### 7.1 Schema 解析

**POST `/api/parse`** — 解析 DDL 或 Cypher

```jsonc
// 请求
{
  "source": "CREATE TABLE ...",   // DDL 或 Cypher 文本（多文件可拼接）
  "type": "ddl",                  // "ddl" | "cypher"
  "dialect": "mysql",             // mysql/postgresql/sqlite/...
  "relation_graph": "..."         // 可选：DDL 时附带 Cypher 关系图，自动注入为外键
}
// 响应
{ "schema_id": "...", "schema_type": "relational", "dialect": "mysql",
  "tables": [...], "nodes": [], "relationships": [], "generation_order": [...] }
```

### 7.2 数据生成

**POST `/api/generate`** — 生成数据（覆盖式：每次清空重建表后写入）

```jsonc
{
  "schema_id": "...",
  "row_counts": { "users": 100, "orders": 500 },
  "ai_enabled": false,            // 可选：启用 AI 字段规则推断
  "llm_config": { "base_url": "...", "api_key": "...", "model": "..." } // 可选
}
```

**WS `/ws/generate`** — 流式生成。连接后发送 `{schema_id, row_counts, ai_enabled}`，服务端推送 `{type: "progress"|"preview"|"done"|"error", ...}`。

### 7.3 表关系管理

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/relations/infer` | AI/启发式识别表关系并注入。Body: `{schema_id, ai_enabled?, llm_config?}` |
| POST | `/api/relations/import` | 从 Cypher 导入关系。Body: `{schema_id, cypher, replace?}` |
| GET | `/api/relations?schema_id=` | 列出当前关系 |
| PUT | `/api/relations` | 全量替换关系。Body: `{schema_id, relations:[{child_table,child_col,parent_table,parent_col}]}` |
| GET | `/api/relations/export?schema_id=` | 导出为 Cypher（`text/plain` 下载） |

### 7.4 自定义规则

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/rules/translate` | 自然语言→规则（预览，不落库）。Body: `{schema_id, text, llm_config?}` |
| POST | `/api/rules/from-samples` | 样例数据→规则。Body: `{schema_id, source_type:"sql"|"csv", content, table?}` |
| GET | `/api/rules?schema_id=` | 读取已保存规则 |
| PUT | `/api/rules` | 保存规则。Body: `{schema_id, field_specs}` |

### 7.5 导出

**POST `/api/export`** — Body: `{schema_id, format: "csv"|"json"|"sql"|"xlsx"}`。CSV/XLSX 返回二进制（ZIP/工作簿），SQL/JSON 返回文本。

### 7.6 内嵌库查询

### 7.7 AI / MySQL / 系统

| 方法 | 路径 | 说明 |

## 8. 数据生成流水线

```
DDL/Cypher 文本
   │  POST /api/parse
   ▼
解析 → RelationalSchemaModel ──(可选)注入 relation_graph 关系──► 存入 SchemaRegistry
   │                                                              │
   │  (可选) 配置关系 / 自定义规则                                  │ DuckDB: CREATE OR REPLACE TABLE
   │  POST /relations/*  ·  POST /rules/*                          │
   ▼                                                              ▼
POST /api/generate (或 WS /ws/generate)
   │
   ├─ 1. CREATE OR REPLACE 重建表（清空旧数据）
   ├─ 2. ConstraintSolver：从 FK 推导关系 + 传递根解析
   ├─ 3. (可选) AI 种子推断 field_specs
   ├─ 4. 合并自定义规则（优先级最高）
   ├─ 5. 按拓扑顺序逐表生成：
   │        关系FK采样 → 自定义/AI规则 → 中文注释语义 → 类型回退
   │        权威列注册值池 → 子列采样（闭环）
   └─ 6. 临时CSV + read_csv_auto 批量写入 DuckDB
   ▼
POST /api/export  或  POST /api/db/sql  或  POST /api/mysql/write
```

## 9. 部署与使用方法

### 9.1 环境要求

- Python ≥ 3.11（推荐用 [uv](https://github.com/astral-sh/uv) 管理）
- Node.js（前端构建）
- 操作系统：Windows / macOS / Linux

### 9.2 后端安装与启动

```bash
cd backend
uv sync                       # 安装依赖（可选图库：uv sync --extra graph）
# 启动开发服务
.venv/Scripts/uvicorn main:app --host 127.0.0.1 --port 8000   # Windows
# 或
uvicorn main:app --reload --port 8000                          # 类 Unix
```

可选配置（环境变量，前缀 `DATAFORGE_`，或 `backend/.env`）：

```
DATAFORGE_LLM_BASE_URL=https://api.openai.com/v1
DATAFORGE_LLM_API_KEY=sk-...
DATAFORGE_LLM_MODEL=gpt-4o
DATAFORGE_DUCKDB_PATH=...        # 默认 backend/data/dataforge.duckdb
```

### 9.3 前端构建

```bash
cd frontend
npm install
npm run build      # 产物输出到 frontend/dist，由后端 StaticFiles 托管
# 或开发模式
npm run dev
```

### 9.4 一键脚本（Windows）

项目根目录提供 `scripts/start.ps1`（构建前端 + 启动后端）与 `scripts/start-dev.ps1`（开发模式）。访问 `http://localhost:8000`。

### 9.5 典型使用流程（前端界面）

1. **Schema**：粘贴或导入 DDL（多文件会自动拼接解析）→ 解析。
2. **表关系图谱**：点「AI 识别关系」自动识别，或「导入 Cypher」导入关系图；在图与表格中查看、编辑；可「导出 Cypher」。
3. **自定义规则**（可选）：用自然语言描述规则并「AI 解析」，或「从样例数据识别」（粘贴 INSERT/CSV），或手动添加；保存。
4. **AI 配置**（可选）：填写 OpenAI 兼容的 base_url / api_key / model 并测试连通性。
5. **Generate**：为各表设置行数 → 生成（支持流式模式实时进度）。
6. **数据预览 / SQL Explorer**：查看与查询生成结果。
7. **导出 / MySQL 写入**：导出 CSV/JSON/SQL/Excel，或直接写入外部 MySQL。

### 9.6 命令行端到端脚本

`backend/run_e2e_test.py`：合并 `test_ddl/` 下所有 DDL + 注入 `schema_graph.cypher` 关系 → 生成 → 校验 JOIN 闭环 → 导出 CSV 到 `output/`。加 `--ai` 启用 AI 种子层。

```bash
cd backend && .venv/Scripts/python run_e2e_test.py        # 纯规则
cd backend && .venv/Scripts/python run_e2e_test.py --ai   # 启用 AI
```

## 11. 测试

```bash
cd backend
.venv/Scripts/python -m pytest ../tests/phase1 ../tests/phase2 ../tests/phase3 \
    ../tests/phase4/unit ../tests/phase5 -q          # 单元 + 不依赖服务器的测试
```

- **单元测试**：DDL/Cypher 解析、约束求解、Faker 规则、批量分块、多方言等。
- **集成测试**（`tests/**/integration`、`tests/e2e`）：通过 HTTP 调真实运行的服务（需先启动 `uvicorn`，连 `localhost:8000`）。

> 注意：集成测试依赖运行中的后端服务；若未启动会出现 `ConnectError`，这是环境问题而非代码缺陷。

## 12. 已知限制与注意事项

- **生成为覆盖式**：每次 `/api/generate` 用 `CREATE OR REPLACE TABLE` 重建所有表，本次未参与生成（行数为 0）的表也会被清空；暂不支持"只重生成部分表、保留其余"或"追加"。
- **AI 为可选增强**：自然语言→规则、AI 关系/字段推断需配置可用的 OpenAI 兼容 LLM；不可用时自动降级（样例识别与统计推断**不需要** AI）。
- **关系闭环依赖关系定义**：闭环建立在已识别/导入/编辑好的表关系之上；关系缺失或方向错误会影响闭环，可在「表关系图谱」页修正。
- **Doris 主键为展示用途**：`DUPLICATE KEY` 不保证唯一，仅作为主键展示与元数据，不强制单列唯一。
- **示例数据敏感性**：`test_ddl/` 含真实银行表结构，作为测试输入随仓库分发，请按需评估是否公开。
